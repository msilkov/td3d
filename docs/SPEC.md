# td3d — спецификация MVP

- **Статус:** draft, до начала реализации
- **Версия:** 0.1 (2026-09-05)
- **Репозиторий:** https://github.com/msilkov/td3d

Документ — источник истины по MVP. Реализация идёт строго по нему; отклонение —
повод сначала обновить спеку, потом писать код. По ходу работы спека правится по факту,
чтобы на выходе получилась готовая документация, а не археология по коммитам.

## 1. Цель

Играбельный 3D tower defense в браузере: волны врагов идут по фиксированному пути,
игрок строит башни за заработанные деньги, башни автоматически стреляют по врагам.
Победа — пережить все волны, поражение — потерять все жизни.

**Бюджет: 12 часов (одни выходные).** Это жёсткое ограничение, из которого выведён
весь остальной документ. Первые ~2 часа уйдут на three.js-концепции, а не на игру.

**Вторая цель:** обкатать R3F перед большим проектом. Поэтому важнее, чтобы подсистемы
получились переиспользуемыми, чем чтобы игра была глубокой.

## 2. Scope

### В MVP входит

- Один уровень с фиксированным путём
- Один тип врага, один тип башни
- Волны врагов по таймеру
- Постройка башен в предустановленные слоты за деньги
- Экономика: доход за убийство, стоимость башни
- Жизни базы, экраны Win/Lose, рестарт
- Модели из CC0-пака вместо примитивов
- Деплой на Vercel

### Не входит — сознательно

Каждый пункт стоит минимум вечер и не нужен для играбельности:

апгрейды и продажа башен · несколько типов врагов и башен · звук и музыка ·
главное меню и настройки · сохранения · несколько уровней · партиклы и постобработка ·
анимации моделей · мобильное управление · бэкенд.

### Технические упрощения и их цена

| Упрощение | Вместо чего | Что экономит |
|---|---|---|
| Слоты под башни | свободное размещение | raycast в плоскость земли, снап к сетке, валидация места |
| Hitscan-урон | летящие снаряды | баллистика, упреждение, пул снарядов, коллизии |
| Фиксированная кривая пути | pathfinding | A\*, navmesh, перестроение маршрута при застройке |

Ни одно из них не мешает игре быть игрой. Все три обратимы, если проект пойдёт дальше.

## 4. Архитектура состояния

Центральное решение, от которого зависит производительность.

**Два уровня состояния, разделённые по частоте изменений:**

| | Где живёт | Что там | Частота |
|---|---|---|---|
| Покадровое | `useRef`, мутация в `useFrame` | позиция врага на кривой (`t`), таймеры перезарядки башен | 60/сек |
| Событийное | zustand | деньги, жизни, номер волны, статус, список башен, список живых врагов | разы в секунду |

**Правило:** ничего, что меняется каждый кадр, не попадает в React state. Позиции врагов
в `useState` = ререндер дерева 60 раз в секунду и мгновенная просадка FPS. Это единственная
ошибка, которая реально ломает R3F-проекты у React-разработчиков.

Спавн и смерть врага — событие, оно идёт через zustand: список меняется несколько раз
в секунду, это нормальный React-ререндер. Движение между этими событиями — в ref.

Если на 30+ врагах просядет FPS — оптимизация следующего уровня: пул из N фиксированных
мешей с `visible={false}` для неактивных, тогда React-дерево вообще перестаёт меняться.
В MVP не делаем заранее.

## 5. Модель данных

### Конфиг уровня — статика, `src/game/config/level1.ts`

```ts
type Vec3 = [number, number, number]

type WaveConfig = {
  count: number      // врагов в волне
  interval: number   // секунд между спавнами
  enemyHp: number
  enemySpeed: number // единиц пути в секунду
  reward: number     // денег за убийство
}

type TowerType = {
  id: string
  cost: number
  range: number      // радиус в мировых единицах
  damage: number
  cooldown: number   // секунд между выстрелами
}

type LevelConfig = {
  path: Vec3[]         // контрольные точки кривой, ~8 штук
  slots: Vec3[]        // позиции слотов под башни
  waves: WaveConfig[]
  startMoney: number
  startLives: number
}
```

### Рантайм — `src/game/store.ts` (zustand)

```ts
type Enemy = { id: number; hp: number; t: number }  // t — прогресс по кривой 0..1
type PlacedTower = { slotIndex: number; typeId: string }

type GameStore = {
  money: number
  lives: number
  waveIndex: number
  status: 'idle' | 'playing' | 'won' | 'lost'
  enemies: Enemy[]
  towers: PlacedTower[]

  spawnEnemy(hp: number): void
  damageEnemy(id: number, amount: number): void   // при hp<=0 — удалить и начислить reward
  enemyReachedBase(id: number): void              // удалить, lives--
  buildTower(slotIndex: number, typeId: string): void  // проверить money и занятость слота
  nextWave(): void
  reset(): void
}
```

`Enemy.t` в сторе — источник истины для спавна/смерти, но **обновляется не каждый кадр**:
внутри `useFrame` двигаем локальный ref, а в стор пишем только при событиях
(смерть, достижение базы).

## 6. Структура компонентов

```
src/
  game/
    config/level1.ts     LevelConfig
    store.ts             zustand
    curve.ts             CatmullRomCurve3 из path, экспорт getPointAt
    useWaves.ts          таймеры волн и спавна
  components/
    Scene.tsx            Canvas, ортокамера под изо-углом, свет, пол
    Ground.tsx           плоскость + визуализация дороги
    Enemy.tsx            один враг: движение по кривой в useFrame
    Enemies.tsx          маппинг store.enemies → <Enemy>
    Slot.tsx             кликабельный слот, onClick → buildTower
    Tower.tsx            поиск ближайшей цели в радиусе, урон по кулдауну
    HUD.tsx              HTML-оверлей: деньги, жизни, волна
    EndScreen.tsx        Win/Lose + рестарт
  App.tsx
```

HUD и EndScreen — обычный HTML поверх `<Canvas>`, не `<Html>` из drei:
для плоского оверлея это проще и дешевле.

## 7. Этапы и критерии приёмки

Порядок не переставлять: 7.1–7.3 дают «что-то живое двигается по экрану» уже к середине
субботы — главный источник мотивации в проекте выходного дня. Замена примитивов на модели
стоит последней сознательно: до 7.7 игра важнее красоты.

| # | Этап | Критерий приёмки |
|---|---|---|
| 7.1 | Сцена: `<Canvas>`, `OrthographicCamera` под изо-углом, пол, свет | Карта видна целиком, сцена рендерится без ошибок в консоли |
| 7.2 | Кривая пути, куб едет по ней от старта до базы | Куб доезжает до конца за предсказуемое время, `lives` уменьшается на 1 |
| 7.3 | Волны: N врагов с интервалом, следующая волна по таймеру | Три волны подряд отрабатывают без вмешательства |
| 7.4 | Башня: радиус, выбор ближайшей цели, урон по кулдауну | Башня из хардкод-координат убивает врагов; на 30 врагах FPS не проседает |
| 7.5 | Слоты + постройка по клику, доход за убийства | Строятся 2–3 башни, деньги списываются и начисляются, в занятый слот построить нельзя |
| 7.6 | HUD + экраны Win/Lose с рестартом | Полный цикл поражения и перезапуска без перезагрузки страницы |
| 7.7 | Баланс: HP, урон, цены, состав волн | Проигрывается при бездействии; выигрывается при разумной игре; не выигрывается автоматически |
| 7.8 | Модели Kenney вместо примитивов | Выглядит как игра, а не как прототип |

## 8. Definition of Done

MVP закрыт, когда выполняется всё:

1. `npm run dev` — консоль чистая, ошибок three.js нет.
2. Волны идут, башни стреляют, экономика работает.
3. Бездействие → Lose; разумная игра → Win; рестарт работает с обоих экранов.
4. `npm run build && vercel deploy --prod` — играется по ссылке в чужом браузере.
5. README со скриншотом + запись экрана 30–60 секунд.
   **Без пункта 5 проект в портфолио не считается положенным** — смотрят видео и ссылку,
   а не исходники.

## 9. Бэклог после MVP

Порядок под режим «несколько часов в неделю», по одной системе за раз:

1. 2–3 типа башен с разными ролями (урон / замедление / площадь)
2. Апгрейды башен
3. Звук: выстрелы, смерть врага, начало волны
4. Второй уровень + выбор уровня
5. Главное меню

## 10. Открытые вопросы

- Визуализация выстрела при hitscan: линия на 100 мс, вспышка или поворот башни к цели?
  Решается на 7.4 по факту, влияет только на ощущение от игры.
- Нужен ли предпросмотр радиуса при наведении на слот? Дёшево и сильно помогает
  читаемости — кандидат в MVP, если 7.5 закроется быстро.
